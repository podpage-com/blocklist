Blocklist

Shared infrastructure for exchanging IP abuse observations between independent organizations.

You keep your existing blocklist. Blocklist lets participating organizations tell each other what they're seeing. What you do with that information is entirely up to you.

Blocklist distributes intelligence. It does not make blocking decisions, manage firewalls or WAFs, or replace your existing abuse-detection system.

How it works

Each participant already has its own way of detecting abuse and deciding which IP addresses to block. Blocklist sits between those independent systems as a shared source of evidence.

Your abuse system
      │
      │ observations you contribute
      ▼
   Blocklist
      │
      │ observations from the network
      ▼
Your own policy and enforcement

A report is evidence, not a verdict. If a participant reports an IP, Blocklist is saying that organization reported that address for a particular reason at a particular time — not that every participant should block it.

Contribute observations

When your system identifies abusive traffic, you can contribute that observation to the network. There are two common integration patterns.

1. Event-based

Call the API when your system adds or updates an IP.

POST /api/v1/observations/
{
  "ip_address": "203.0.113.42",
  "reason": "signup_abuse",
  "last_seen_at": "2026-09-18T05:00:00Z"
}

2. Periodic synchronization

If your system already maintains an authoritative blocklist, periodically send the complete current list.

PUT /api/v1/observations/sync/
{
  "observations": [
    {"ip_address":"203.0.113.42","reason":"spam"},
    {"ip_address":"198.51.100.7","reason":"scraping"}
  ]
}

The sync endpoint is authoritative for your organization. Anything you previously reported that is no longer present becomes inactive. This is often the simplest integration because your existing system remains the source of truth and the two systems cannot silently drift apart.

Independent evidence vs. shared intelligence

It is important not to mistake propagation for corroboration. If Organization A independently detects abuse, and Organizations B and C subsequently block that IP because they learned about it through Blocklist, that is still one independent observation — not three.

Organization A detects abuse ───────► independent evidence
                                      │
                                      ▼
                                  Blocklist
                                   /      \
                                  ▼        ▼
                         Organization B  Organization C
                         blocks from     blocks from
                         shared intel    shared intel

Integrations should distinguish IPs blocked because of independently observed abuse from IPs blocked because of Blocklist or another external intelligence source. Network-derived actions should never be treated as additional independent corroboration.

The protocol is being designed to preserve this distinction explicitly so participants can reason about independent reports separately from adoption of shared intelligence.

Use network intelligence

You decide how much weight to give reports from other participants. Blocklist can be used as confirmation, as one input to a risk score, or as a source for automated policy.

Example policyPossible action
1 independent organization reports an IPFlag it or increase its abuse score
2+ independent organizations report an IPAutomatically block it
Your system detects suspicious behaviorQuery Blocklist to see whether anyone else has observed the IP
Report is older than your acceptable windowIgnore it
IP is on your local allowlistIgnore network reports

Simple lookup integration

You do not need to ingest the entire network feed. A minimal integration can query Blocklist only when your own system sees something suspicious.

Your system flags 203.0.113.42
            │
            ▼
GET /api/v1/ips/203.0.113.42/
            │
            ▼
See whether other organizations
have independently observed it

Continuous feed integration

More sophisticated consumers can process the change feed and maintain a local view of network intelligence, then apply their own thresholds and policies.

GET /api/v1/changes/?since=2026-09-18T05:00:00Z

API reference

Every organization receives an API key. Send it as Authorization: Api-Key YOUR_KEY.

EndpointPurpose
POST /api/v1/observations/Report or update an observation
PUT /api/v1/observations/sync/Synchronize your authoritative current observations
GET /api/v1/observations/Browse current active network observations
GET /api/v1/ips/<ip>/Inspect evidence for one IP
GET /api/v1/changes/?since=...Consume incremental network changes
GET /health/Service health

Observation queries can be filtered by IP, reason, and reporter. Change-feed consumers should follow the returned cursor when additional results are available.

Consumer policy

Blocklist deliberately does not define a universal threshold for blocking. A participant may require multiple independent reports, use reports only as a risk signal, maintain local allowlists, restrict which abuse categories matter, or take no automated action at all.
